# Windows 与麒麟独立发布（1.0.22）

## 发布目标

后台“版本更新”分为 Windows、信创两个入口；信创按 x86_64、ARM64 选择架构。版本记录的标识为平台、架构和版本号，三个目标可发布同一业务版本而不互相覆盖。

| 显示目标 | platform | arch | installer | 产物 |
| --- | --- | --- | --- | --- |
| Windows 通用版 | win32 | x64 | nsis | EXE，安装时选择 Win7 或 Win10/11 内核 |
| 麒麟 x86_64 | linux | x64 | deb | DEB，内部 Architecture=amd64 |
| 麒麟 ARM64 | linux | arm64 | deb | DEB，内部 Architecture=arm64 |

Windows 保留旧中文安装包、DataFusion-Setup 和兼容通用安装包三种规范名称。麒麟正式名称为 `数据融合助手-麒麟版-版本-架构.deb`，同时接受原来的“麒麟测试版”名称。

## 兼容与数据迁移

既有更新记录、托管文件和 OSS 对象保持原样，旧记录默认归入 Windows x64。数据库增加目标字段，将原托管版本唯一约束改为目标和版本组合；旧客户端不传目标时只获取 Windows x64。签名设备授权、在线更新权限及账号权限校验保持有效。

生产环境的宿主机 Python SQLite 版本过旧，不支持新索引语法；检查、备份和迁移应使用服务实际运行的 Node24 SQLite。部署先在生产库副本运行迁移并核对原字段摘要，再停止单个后台容器、保留数据库备份、替换发布相关代码并恢复服务。客户、授权、设备身份、企业信息和既有发布记录均作原字段核对。

本次线上部署从实际运行代码合入发布相关变化；本地尚未上线的企业导入定时器未随本次发布部署。现有 Docker 配置、HTTPS、OSS 配置、访问范围及其他应用保持原配置。

## 上传与分发

上传接口显式携带 platform、arch；后台从 DEB 的 ar/control/data 元数据核验包名、内部版本和 ELF 架构，不执行包内脚本。Linux 版本要求完整托管上传，包含签名文件长度，不支持外链发布。Windows 既有外链记录继续兼容。

新 OSS 对象按平台、架构、版本分目录，旧对象路径继续可用。发布前验证文件长度及 SHA256；已存在的目标版本不得替换。草稿不出现在客户端清单中。ARM64 初次上传时留作草稿，后续模拟环境验证和用户授权发布的记录见下文；物理 ARM 设备尚未验收。

## 客户端更新

客户端请求携带当前版本、系统、芯片架构及原有签名设备凭据。除了验证清单签名和 SHA256，还独立拒绝不匹配的平台、架构、扩展名和安装器类型。下载缓存按平台与架构区分。

Windows10/11 沿用验证后的交接、保存会话、正常退出、安装及重启流程。Win7 配套交接助手已改为 CLR2/.NET3.5 并通过该运行时测试；在 Win7 实机验证在线交接前，客户端仍保留手动升级提示。

麒麟支持自动检查和后台下载；用户确认时再次检查发布状态、权限、摘要和 DEB 的包名/版本/架构。保存数据后打开系统软件安装程序，由用户完成系统安装确认。优先使用麒麟软件商店，兼容 GNOME Software 和桌面默认打开方式；启动失败会重开原应用，不伪报安装成功。旧 1.0.20 麒麟版需先手动安装本版一次。

## 麒麟包构建

先用对应架构的官方 Linux Electron 分发构建目录，并运行 `verify-linux-package.mjs`。`stage-kylin-deb.mjs` 生成独立的 DEB 暂存目录；`build-kylin-deb.py` 可在 Windows/Linux 上生成 GNU tar + XZ 格式 DEB，不要求目标电脑执行构建脚本。ar 成员名不添加尾随斜杠；归档不使用 PAX 扩展头，以兼容麒麟 V10 的旧版 dpkg。

```text
python scripts/build-kylin-deb.py --arch x64
python scripts/build-kylin-deb.py --arch arm64
```

打包验证检查所有载荷字节、root 归属、目录/文件权限、主程序和 sandbox 权限；不执行目标 ELF 或维护脚本。麒麟自己的包信任检查仍在正常安装时执行，不更改其安全策略。

发布服务需要 GNU tar 和 xz-utils。生产专用运行镜像从原 Node 镜像固定摘要派生，仅新增 xz-utils；Node 版本及现有系统包保持原样。镜像选择持久记录在 `/etc/data-fusion/runtime-image.env`。更新运行镜像时沿用原容器的配置、限制、只读代码挂载、数据挂载、环境和网络地址，保留旧容器回滚。此次切换前后 15 张业务表摘要一致，HTTPS 与原代理配置保持不变。

### 麒麟 V10 安装诊断（2026-11-11）

昨日 1.0.20 与初次构建的 1.0.22 均未签名，不能将失败直接归因为缺少签名证书。麒麟日志显示：昨日安装的单次安全授权结果为 allow；今日两次桌面安装的安全确认在 30 秒后超时，结果为 forbid。通过系统原生单次授权确认后，初次 1.0.22 包进一步报出“不支持的 PAX tar 头部类型 x”，这是新封装格式与该机旧 dpkg 的兼容问题。

构建器已改用 GNU tar + XZ。独立验证器检查原始 tar 头，避免 Python tarfile 隐藏 PAX 扩展头导致误判；回归覆盖中文长文件名。单次安装授权只针对已核对 SHA256 的本次包，不使用 force 选项、不修改全局来源校验、不购买或伪造签名来处理这个格式问题。初次失败升级由 dpkg 回滚，原 1.0.20、数据库、授权、加密会话均保持原值。

修正后的 x86_64 包已在原机完成 1.0.20→1.0.22 覆盖升级。原授权有效；28 条本地记录、56 条记录版本、28 条任务输出按表逐行摘要相同，28 条法人和信用代码保留。大件运输 API 会话验证为 authenticated；实际导出一条无警告、无必填缺项的 Excel，32 列及 24 处模板合并区域检查通过。已正常关闭并以无调试参数方式重新打开，诊断端口关闭。测试授权原本未开通自动更新，保持该权限原值；更新分发需另以具备权限的设备证明检查。ARM64 未实机运行。

- 后台完整基线111项，最终发布/OSS目标相关27项及补充压缩回归通过。
- 管理界面39项单元测试、158项真实界面检查，覆盖1440/1180/600像素及三个目标隔离。
- Windows 更新交接：现代 CLR4、兼容 CLR2 各24项，未在 Win7 实机运行交接。
- 两个修正后的实际 DEB 均通过独立载荷/权限/GNU tar 核验；便携构建器10项测试通过。ARM64 仅静态验证。
- Windows 与 Linux x64 实际包分别完成隔离环境上传、发布、签名清单、完整下载和 Range 验证；不调用付费企业接口。

本轮生产部署及发布证据保存在 `private/deploy/multiplatform-1.0.22-20261111/`；Windows 发布结果见 `publication.json`，麒麟首次发布结果见 `publication-linux.json`。Windows x64 与麒麟 x86_64 的 1.0.22 已发布并通过实际下载 SHA256、签名目标清单与业务数据保护核对。ARM64 首次上传为私有草稿，后续发布结果见 `publication-arm64.json`。旧 1.0.20 麒麟客户端需手动安装 1.0.22 一次；后续更新仍需授权开通在线更新权限。麒麟安装修复及数据保留证据见 `kylin-compatibility-resolution.json`，后台运行镜像切换证据见 `runtime-deployment.json`。

### ARM64 模拟环境补充验证（2026-11-11）

在独立 QEMU TCG 环境启动官方麒麟 V10 SP1 ARM64 Live 镜像，内核报告 `aarch64`，实际安装并运行 ARM64 1.0.22。后台签发了绑定模拟机的七天测试授权，仅开放大件运输、从业人员及导出；原 Windows 授权未修改，ARM64 正式更新仍为私有草稿。

已验证实际工作台、授权组件列表、HTTPS 后台连接，以及大件运输与从业人员两个真实登录页的独立标签页加载。原生 SQLite 读取及应用导出使用一条明确标注“模拟数据，禁止报送”的本地测试记录：Excel 导出无缺项警告，ZIP 完整性、32 列及 24 处合并区域检查通过，打开目录接口成功。此记录直接作为测试夹具写入空白本地台账，没有执行原系统查询或回流，没有调用企业付费补全接口。正常关闭并重开应用后，授权文件摘要不变、测试记录保留；随后已精确清理该测试记录，应用无诊断参数重新启动，9331 端口关闭。

Live 会话初始没有密钥环，首次打开业务页出现系统创建密钥环提示；仅为该独立测试用户初始化了新的加密密钥环，未迁移 Windows 密码或会话，未修改全局安全策略。普通安装系统的密钥环、登录会话恢复和系统重启持久化仍需独立验证。

本轮没有完成真实业务账号登录、真实回流、在线企业补全、ARM64 DEB 覆盖升级或物理 ARM 设备验收；模拟环境中的软件图形回退也不能证明飞腾、鲲鹏设备的 GPU 兼容性及性能。详细证据见 `private/deploy/arm64-qa-20261111/progress.json` 及对应串口结果和截图。

### 三个平台发布状态（2026-11-11 17:20，Asia/Shanghai）

用户在知悉上述 ARM64 验证范围后要求上线，已通过后台正常发布接口启用原 ARM64 1.0.22 草稿，未替换安装包。发布说明写明已通过的模拟环境检查，以及真实账号回流、企业补全、覆盖升级和飞腾/鲲鹏实机尚未验收。现有版本状态接口只能更改启停状态，草稿说明通过一次受限事务修正，修改前版本行已备份并留下管理审计；发布启用仍走管理员登录、验证码和密码复核接口。

Windows 通用版、麒麟 x86_64、麒麟 ARM64 三个通道均返回 1.0.22。已验证旧 Windows 请求和三个显式目标的清单签名、目标及文件摘要；三个公开下载入口均通过 Range 与安装包头检查，ARM64 完整下载的 89,721,232 字节及 SHA256 与本地原包一致。OSS 的签名 GET 地址需用 GET/Range 校验，直接改用 HEAD 会因签名方法不匹配而返回 403。
