# 架构决策与待确认事项

## 已确定，不再反复讨论
1. Electron 桌面应用。
2. 应用无用户账号登录，仅 License 密钥激活。
3. 用户必须在应用内登录具体业务系统后才能查询该系统。
4. 登录产生的 Token/Cookie/Session 由业务插件管理。
5. Renderer 不直接获得原始认证材料。
6. 业务数据全部本地保存。
7. 产品公网服务不接触业务数据，只负责授权、版本和插件更新。
8. 一个业务系统一个插件，一个系统内包含多个业务事项。
9. 每个事项独立查询 Schema、字段、唯一键和同步策略。
10. 本地同步区分新增、更新、无变化，并保存状态/字段历史。
11. 查询复杂度由插件承担，主程序只提供统一运行框架。

## 当前默认方案（真实系统接入前可调整）
- 本地数据库：SQLite。
- UI：React + TypeScript。
- 主进程负责敏感会话、数据库、文件和网络插件运行。
- Preload 提供白名单 IPC。
- 长查询进入 Task Engine。
- License 使用非对称签名，客户端仅持有公钥。
- Token 默认只驻留内存；需要跨重启保持登录时使用操作系统安全凭据存储。

## 后续需要真实场景确认
- 首个业务系统的真实登录方式。
- 是否需要嵌入 WebView/BrowserWindow 完成 SSO/扫码登录。
- 各系统是否允许会话跨软件重启保存。
- SQLite 是否需要整库加密。
- 部门是否要求数据导出审计日志。
- 自动同步是否需要在软件启动后后台执行。
- License 是否必须支持完全离线环境。
- 更新服务器部署位置与签名证书。
- Windows 是否为唯一首发平台。

## 开发原则
遇到未确认项时，优先设计接口和扩展点，不提前把某个业务系统的特例写进核心层。
