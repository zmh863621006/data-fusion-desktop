# 启动业务更新运维说明

本文对应 1.1.0 起引入的固定基础包与业务 ASAR 更新机制。构建命令与产物结构见 [固定基础包与业务 ASAR 构建](30-business-payload-packaging.md)，旧完整安装包的分发说明见 [后台生产部署](18-admin-production.md)。本文是待发布功能的运维说明，不代表已经部署后台、上传 OSS 或切换线上客户端。

## 一次性基础包迁移

旧客户端没有固定启动器，不能仅靠下载业务 ASAR 获得本机制。首次迁移仍需安装一次对应系统的完整基础包；可以在原完整安装包通道发布该基础包，让旧客户端按原流程升级，也可以人工安装。保留应用身份和原用户目录，升级前保存工作、备份业务数据与导出文件，并按原安装器要求关闭占用的文件。

新基础包的 `resources/app.asar` 是固定启动器，包含信任公钥、启动页面、更新校验逻辑及固定 OSS 入口。初始业务包在 `resources/business/builtin.asar`，其 SHA256、大小、版本和后台配置钉在基础包内部。后续业务更新放入用户目录的新版本文件夹，校验后加载；不覆盖已安装的基础 `app.asar`，也不在运行中替换当前业务文件。

业务 ASAR 可以更新业务主进程、页面、查询与回流逻辑、导出模板和允许打入包内的 JavaScript 依赖。Electron、启动器及其信任公钥、固定 OSS 入口、Windows 图形 DLL、原生数据库组件、麒麟兼容库及安装器仍属于基础包。修改这些组件或提高运行环境要求时，仍需发布新的完整基础包；业务包不是覆盖所有原生运行组件的通用补丁。

同事正在使用应用时可以继续完成当前工作。运行中手动检查会在独立目录准备新版，完成后提示保存工作并重启；存在回流、查询或导出任务时拒绝立即重启。启动强制检查发生在下一次完整启动、业务模块加载之前，不会为了发布新版本直接结束正在运行的客户端。

## OSS 固定入口与发布对象

当前构建默认固定入口为：

```text
https://shenzhen-sjrh.oss-cn-shenzhen.aliyuncs.com/data-fusion/updates/windows-x64/business/v1/
```

`windows-x64` 是既有 OSS 配置前缀的一部分；其下的业务通道仍按实际系统、架构和 Electron 大版本独立区分，不表示所有载荷都是 Windows 包。每个通道结构如下：

```text
<固定入口>/<platform>/<arch>/<variant>/electron-<major>/latest.json
<固定入口>/<platform>/<arch>/<variant>/electron-<major>/<version>/business-<version>.asar
```

| 通道 | platform | arch | variant | electronMajor |
| --- | --- | --- | --- | --- |
| Windows 10/11 | win32 | x64 | standard | 44 |
| Windows 7 兼容基础包 | win32 | x64 | standard | 22 |
| 麒麟 x86_64 | linux | x64 | standard | 44 |
| 麒麟 ARM64 | linux | arm64 | standard | 44 |
| 海思 990 专用 | linux | arm64 | kirin990 | 44 |

这些是协议允许的目标，不能据此认定每个目标都已完成实机验收。同一业务版本可在不同通道独立存在；每个通道必须分别构建、测试、上传和发布，不能把标准 ARM64 包放到海思专用通道。

后台“版本更新”分为“基础安装包”和“业务更新包”。业务包上传时读取实际 ASAR 内的元数据，检查产品、版本、目标、最低基础版本、后台配置、包结构及 SHA256。校验成功只创建私有草稿，OSS 上的 ASAR 对象为 `private`，不会进入公开清单。上传超限、内容无效或账号状态变更不会形成可发布的完整草稿。

超级管理员核对详情并输入当前密码发布后，后台将对应 ASAR 设为 `public-read`，再以条件写入方式更新该通道的 `latest.json`。公开清单为 RSA-SHA256 签名信封，签名内容包括业务版本、最低基础版本、精确目标、固定载荷 URL、字节数、SHA256、后台源地址与修订号。客户端使用基础包内的产品公钥验签，并校验实际 ASAR 与内部 `business.json`；HTTPS 下载成功本身不等于校验通过。

已发布清单与载荷使用固定公开 HTTPS 地址，不依赖后台 IP、设备登录或有时效的 OSS 查询签名参数。OSS 中公开的是应用程序文件和签名更新元数据，不应包含授权密钥、账号密码、Cookie、企业台账、业务数据库、导出文件或服务端私钥。启动检查可以在客户端激活前进行；实际业务菜单、查询、导出和后台企业补全仍按原授权规则执行。旧授权中的 `allow_auto_update` 继续控制旧完整安装包接口，不控制新的公开静态业务发现入口。

ASAR 版本对象采用不可覆盖写入及长期不可变缓存；`latest.json` 使用需要重新校验的缓存策略。不要手工覆盖版本对象，也不要将草稿目录整体设为公开。若有 CDN 或代理，应保留清单的缓存策略，并确认它不会持续返回过期清单。

## 配置复用与部署准备

已核对代码，无需新增必填环境变量，也没有新建一套 OSS 密钥或桌面 OSS 凭据。配置关系如下：

| 项目 | 当前行为 |
| --- | --- |
| 本地业务包目录 | 默认 `ADMIN_DB_PATH` 同级的 `business-releases/`；`ADMIN_DB_PATH=/data/admin.sqlite` 时为 `/data/business-releases/`。 |
| 可选目录覆盖 | `ADMIN_BUSINESS_UPDATE_DIRECTORY` 只覆盖业务包本地存储目录，不是公开下载地址；现有 `.env.example` 未要求填写。 |
| OSS 配置文件 | 从业务包目录的上一级读取 `update-oss.secure.json`，与原完整安装包使用相同文件名及格式。默认布局下可直接复用现有配置；若目录覆盖到不同父目录，必须保证该父目录有正确的受保护配置文件。 |
| OSS 配置字段 | 复用 `endpoint`、`bucket`、`prefix`、`accessKeyId`、`accessKeySecret` 和可选 `securityToken`；业务命名空间固定追加 `business/v1/`。 |
| 签名私钥 | 复用 `ADMIN_LICENSE_PRIVATE_KEY` 指向的现有产品 RSA 私钥。必须与基础包钉住的产品公钥匹配，不生成新的临时生产密钥。 |
| `ADMIN_UPDATE_PUBLIC_ORIGIN` | 仍供后台返回的兼容下载代理源地址使用，默认继承 `ADMIN_PUBLIC_ORIGIN`；不决定 OSS 静态发现入口。 |
| 桌面固定发现入口 | 基础包生成 `shell.json` 时写入；默认值见上文，可在构建基础包时通过 `stage-business-shell.mjs --feed-base` 指定。 |
| `DATA_FUSION_UPDATE_URL` | 保留为旧完整安装包清单接口配置，不能用它改写固定启动器的 OSS 发现入口。 |

服务端默认路径在宿主机为 `/var/lib/data-fusion/update-oss.secure.json`，使用现有数据挂载的容器中为 `/data/update-oss.secure.json`。文件保留原服务账号和 0600 权限，不放进 Git、静态站点、安装包或日志。配置在服务启动时加载，修改配置后需按正常发布流程重启后台。

“复用配置格式”不等于原 RAM 权限已经满足新操作。正式接通前应核对该身份可访问原 `prefix` 下新增的 `business/v1/` 对象，具有需要的对象读写、HEAD 校验及 `PutObjectACL` 权限；若策略只允许原安装包路径，需补充新前缀。还需确认 Bucket 的阻止公共访问策略允许只公开已发布对象。无需开放整个 Bucket，也无需增加允许公开列举目录的权限。本轮本地测试未在线核实生产 RAM 或 Bucket 策略。

固定启动器的 `feedBase` 必须与后台根据实际 `endpoint/bucket/prefix` 生成的 `feedBase` 一致。后台 API 的 `configured=true` 仅说明加载到了 OSS 配置，不代表线上访问权限、公开下载、TLS 或网络已经验证。未配置 OSS 时可以保存本地业务草稿，但不能发布；这与旧完整安装包可以使用本地分发的行为不同。

数据库加法新增 `business_releases` 和 `business_release_channels`，保留旧客户、授权、设备、企业与完整安装包发布记录。正式部署需备份数据库、原代码、环境与受保护配置，并仅合入本功能所需模块和后台构建产物。后台上传反向代理需为 `/api/admin/business-releases/upload` 配置 256 MB 上限、关闭请求缓冲及 600 秒代理等待；业务发布 PATCH 路径需 180 秒等待。参考现有部署示例核对，不能直接覆盖线上 Nginx 配置、访问策略或其他站点。

## 启动强制更新与离线规则

启动器先验证当前本地版本，再读取本通道清单，业务界面此时尚未运行。主要行为如下：

| 情况 | 行为 |
| --- | --- |
| 网络失败、超时或服务暂不可用，未记录必须完成的新版本，本地版本校验通过 | 使用已校验的本地版本；首次可使用基础包内钉住的初始业务包。下次启动继续检查。 |
| 清单签名、目标、结构或本地状态无效 | 阻止进入业务界面，显示重试/退出；不把校验失败当作可忽略的离线状态。 |
| 已确认有兼容的更高业务版本 | 原子写入签名 `pending.json`，随后下载、核验、准备新版；完成后才进入业务界面。 |
| 已有 pending，随后断网或下载失败 | 保留 pending，必须完成更新；不能用“断网”跳过已确认的新版本。可重试或退出后再试。 |
| 清单后来变旧，但本机已有更高 pending | 保留更高 pending，避免服务端清单回退绕过强制更新。 |
| 新版要求更高 `minShellVersion` | 当前启动提示获取匹配的新基础包；业务 ASAR 不替代基础运行环境升级。 |
| 下载与校验成功 | 原子切换 `state.json`，成功后移除 pending，再加载已验证的新业务版本。 |

pending 是启动更新状态，不是“记住登录”。不能通过运维脚本删除 pending 或重写 state 来规避强制更新。若签名状态损坏、目标不匹配或基础运行环境不满足要求，应修复服务或安装正确基础包，不能关闭校验继续加载。

用户目录中的通道状态位于：

```text
<userData>/updates/business/<platform>-<arch>-<variant>-electron-<major>/
  pending.json
  state.json
  startup.jsonl
  payloads/<version>-<sha256前16位>/business.asar
  payloads/<version>-<sha256前16位>/app/
```

默认 Windows 用户目录为 `%APPDATA%/data-fusion-desktop`；Win7 兼容组件使用 `%APPDATA%/data-fusion-desktop-win7`。Linux 使用 Electron 的 `appData` 下 `data-fusion-desktop`。指定 `--user-data-dir` 时以指定路径为准。启动日志记录状态、版本和受控错误码，超过约 1 MB 后滚动为 `.previous`；定位问题可先收集对应通道的日志、基础版本和业务版本，避免收集账号、会话或密钥文件。

## 损坏缓存的修复与隔离

启动不只检查版本号，也验证缓存 ASAR 的完整摘要、内部元数据及已提取目录的文件树和逐文件摘要。发现缺失、改写或异常文件时，不继续执行这些文件。

冷启动允许自动修复可识别的缓存损坏：先取得完整且通过验证的源载荷，在独立暂存目录准备成功，再把损坏缓存移到同级 `.quarantine-...` 目录并原子切换；初始业务包可从基础包内钉住的 `builtin.asar` 准备。已下载版本需要重新下载修复时，若网络不可用则阻止启动，不能静默加载损坏文件或退回旧业务绕过 pending。

隔离目录保留用于排查，不作为可执行业务目录。若切换失败，代码尽量恢复原目录并保留可诊断状态；无法安全修复时显示错误，不删除整个用户目录。用户授权、账号、Cookie、会话、业务数据库和导出文件与业务缓存分开，不因业务包切换而清空。

`state.json` 的 `previous` 保存上一份签名版本信息，不等于发生故障后自动降级执行。清理隔离或旧版本缓存应在应用退出、确认当前可用并保留必要证据后单独处理；当前流程不会在启动时无差别扫描删除用户数据。

## 版本发布与紧急回退

每个通道的 `version` 使用三段递增版本号，例如 `1.1.0`、`1.1.1`，不使用预发布后缀。同通道同版本不可重新上传不同内容，也不能发布低于历史发布上限的版本。重新点击发布只能用于核对同一不可变产物或协调中断的发布状态，不能替换字节。`latest.json` 的 ETag 条件写入和服务端通道租约共同避免并发旧发布覆盖新发布。

建议的正式发布顺序：

1. 冻结并提交源码，构建目标业务 ASAR，核对摘要、目标、最低基础版本和后台修订；保留可追溯的构建记录。
2. 在隔离环境完成目标系统验收，包括启动、离线、pending 断网恢复、升级后数据与会话保留、关键业务和导出。不能把其他架构或模拟器的结构校验当作目标实体机验证。
3. 在后台选择精确业务通道上传；查看私有草稿详情，核对它确实对应已测试的字节。上传本身不触发客户端更新。
4. 确认发布范围后输入管理员密码发布；从固定 OSS URL 验证公开清单签名、实际包 SHA256 和通道隔离，再验证试点客户端完整启动。
5. 记录已发布业务版本、基础版本、通道、SHA256、后台修订和验收结果，逐通道推进。

当前通道头版本不能直接下线。若新业务逻辑有问题，应取已验证的旧业务源码修复或恢复内容，但赋予一个**更高业务版本号**重新构建、测试并发布。例如 `1.1.2` 有问题，就把恢复后的业务作为 `1.1.3` 发布，不能把清单改回 `1.1.1`，也不能覆盖 `business-1.1.2.asar`。先确认新修复版本成为通道头，再按需下线历史版本；下线使历史对象回到私有，但不会撤销已下载到客户端的文件。

紧急回退时也要保留不降低的后台配置修订，不能把旧源码中较低的后台 revision 一并带回。若旧内容依赖已经变化的数据结构，应做兼容修复；更高版本号不会自动解决数据兼容问题。

## 后台 IP 或入口迁移

业务更新检查直接访问固定 OSS，故后台 IP 变化不要求先连上旧后台才能找到新版。迁移时先使新后台的 HTTPS、接口、原授权/企业数据、产品签名私钥及所需运行配置就绪，并保留旧入口供存量旧完整安装包客户端使用。

在新的更高业务版本中，构建时设置：

```powershell
node scripts/build-business-payload.mjs --version 1.1.1 --platform win32 --arch x64 --variant standard --electron-major 44 --min-shell-version 1.1.0 --backend-origin https://新后台地址 --backend-revision 2
```

这里的版本号、目标和修订号均为示例，实际 revision 必须高于该通道已发布与客户端已接受的修订。`backend.origin` 只能是完整 HTTPS 源地址，可包含明确端口，不含路径、查询串或结尾斜线。后台同时检查数据库历史与 OSS 已签名清单：revision 不能降低，相同 revision 不能换 origin；客户端同样拒绝相同修订冲突及需要安装的新包修订回退。

新配置进入实际 ASAR 的 `business.json` 及已签名清单，更新成功后供业务运行时生成授权、授权状态、企业补全等默认接口地址。单独设置过 `DATA_FUSION_ACTIVATION_URL`、`DATA_FUSION_LICENSE_STATUS_URL`、`DATA_FUSION_ENTERPRISE_URL` 或 `DATA_FUSION_UPDATE_URL` 的部署仍优先使用这些显式覆盖值，迁移时需另行核对并调整；不能承诺更新会覆盖人工指定的地址。

后台迁移不应同时随意改 Bucket、前缀、固定 feed URL 或产品签名公钥：这些信任入口在基础包中。若必须迁移 OSS 固定入口或更换信任公钥，需要规划新的基础包及旧入口过渡，不能只靠业务 ASAR 改写固定启动器。不同通道需分别发布包含新后台配置的业务版本；未迁移的旧客户端继续依赖原完整安装包接口。

## 测试与正式发布边界

本功能的本地测试覆盖私有草稿、真实 ASAR 解析、RSA 签名、不可覆盖版本、后台修订单调、权限与 CSRF、并发发布、平台隔离和后台页面。使用 mock OSS、临时数据库、隔离用户目录或 `.tmp/` 产物的结果，只证明相应测试条件下的行为，不会自动使生产版本生效。

构建完成、安装测试成功、上传草稿、发布业务清单、发布完整基础包，是独立阶段。正式启用需另行完成生产配置与权限核对、备份、后台部署、目标平台基础包迁移和已测试字节的发布。保留旧完整安装包发布页面、接口、历史产物及其授权鉴权规则，既用于存量客户端过渡，也用于以后升级 Electron 或原生组件。没有完成对应阶段时，交付记录应明确写“本地测试”“私有草稿”或“未发布”，不能称已上线。
