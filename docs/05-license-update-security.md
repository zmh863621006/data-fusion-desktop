# 05. 授权、更新与安全方案

## 1. License 目标

应用本身无用户登录。License 用于控制软件使用权，而不是业务系统身份。

License 建议包含：
- license_id
- 客户/部门标识
- 有效期
- 可用系统
- 可用事项
- 最大设备数
- 是否允许导出
- 是否允许自动同步
- 激活模式（online / offline）
- 是否允许自动更新
- 许可证版本

## 2. 离线签名

即使第一版支持联网激活，也建议 License 使用非对称签名：

```text
服务端私钥签发
→ 客户端内置公钥
→ 客户端验证签名
```

私钥永远不进入桌面客户端。

这样即使后续需要短时间离线，客户端仍可验证许可证真实性。

## 3. 在线授权服务

授权管理后台只维护：
- License 状态
- 激活设备
- 吊销状态
- 有效期
- 功能授权

客户端上传的信息应控制在授权所需最低范围，禁止上传业务数据和业务系统 Token。

## 4. 设备绑定

第一版可预留设备 ID 接口。后续实现时避免直接上传过多硬件隐私信息，可对必要的稳定设备特征进行本地组合和哈希。

支持：
- 首次激活
- 最大设备数
- 管理端解绑
- 更换电脑

## 5. License 失效行为

建议：
- 禁止新查询/新同步
- 禁止使用失效授权的业务系统组件
- 已有本地数据仍允许用户查看
- 导出是否允许由业务政策决定

不要因为 License 过期破坏或删除用户本地数据。

## 6. 更新架构

业务系统组件随主程序统一发布，不允许终端用户动态安装代码插件。

```text
更新服务
├─ app-manifest.json
└─ signed app packages
```

客户端启动后：
1. 获取版本清单
2. 比较本地版本
3. 校验兼容性
4. 下载
5. 校验签名/摘要
6. 安装或等待重启

## 7. 在线与离线更新

在线授权且拥有自动更新权限的设备可以获取签名更新清单并自动更新。离线设备由管理员人工安装新版程序。

更新要求：
- 版本清单签名校验
- 安装包完整性校验
- 安装前备份旧版本
- 启动失败自动回滚
- 数据结构变化提供 migration

## 8. 会话安全

优先原则：
- 短期 Token 尽量只驻留内存
- 不把 Token 放 React state、localStorage、普通日志
- 如需跨重启保持登录，使用操作系统安全凭据能力或受保护的本地存储
- SQLite 中不明文保存业务系统密码

## 9. 日志安全

日志默认允许：
- 插件名
- 事项名
- URL path（按实际敏感性处理）
- HTTP 状态码
- 页码
- 数量
- 耗时
- 错误码

日志默认禁止：
- 密码
- 验证码
- 完整 Authorization
- 完整 Cookie
- 完整身份证等高敏感字段

任何调试日志都必须支持脱敏。

## 10. Electron 安全

必须坚持：
- contextIsolation=true
- nodeIntegration=false
- Renderer 不直接访问 fs/net/sqlite
- IPC 白名单
- IPC 参数运行时校验
- 限制外部导航
- 限制任意新窗口
- 不执行远程下发的任意 JS 代码

更新包必须受信任、签名且版本受控，不能从任意 URL 动态执行脚本。

## 11. 数据边界

最重要的网络边界：

```text
用户电脑 ←→ 原业务系统
用户电脑 ←→ 授权/更新服务器
```

但：

```text
原业务数据 ✕ 授权服务器
原系统 Token ✕ 授权服务器
```

两条网络链路在逻辑和存储上保持隔离。

## 12. 合规原则

工具只使用当前用户已获得的业务系统权限执行正常查询，不提供权限绕过能力。真实系统接入前，需要确认对应单位允许的数据留存、导出范围和本地设备安全要求。
