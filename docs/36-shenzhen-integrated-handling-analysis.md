# 深圳一体化办件与办理过程回流分析

2026-11-27，按用户要求离线分析五份新HAR。目标与广东人社街道办四项一致：保存每笔办件及其完整办理过程，用于窗口人员办理记录展示；本轮未实现业务接口、未发送网络请求、未打包或发布。

后续已按用户确认完成[1.1.15本地测试实现](37-shenzhen-integrated-preview-1.1.15.md)，下文保留原始分析依据与当时的验证边界。

## 抓包范围与结论

`账号密码登录.har`记录33个请求，`一体化登录后首页.har`记录14个请求。`账号已办业务.har`与`账号已办业务2.har`各68个请求，文件内容完全相同，不能算作两轮独立验证。`经办业务查询所有列表详情.har`记录103个请求，包含本次所需的“经办业务查询”、两类详情和办理记录请求。

主入口应使用原页面“经办业务查询”的 `queryAllDealtBusiList`。`queryMyDealtBusiList`对应个人已办，不能代替它；`queryBusiInstanceList`用于待办/签领，也不是本次全量经办列表。可见范围始终由当前登录账号及机构权限决定，不通过填写他人账号扩大范围。

## 会话与登录检测

真正的账号密码提交为 `POST /cas/login`，返回302后进入 `/cas/systemList`。系统切换页代码显示，经 `/cas/changeSystem` 打开 `/TRANS/ssologin`；抓包没有记录这段实际令牌签发跳转，不能声称已验证了完整交换协议。业务首页为 `/TRANS/zhsl/home`。

业务请求通过原站 `sessionStorage['access-token']` 填入请求头 `Access-Token`，没有Bearer前缀。CAS的 `SESSION`、`TGC` Cookie主要位于 `/cas/`，不能代替业务令牌。

最小只读会话校验为 `POST /TRANSB/security/getUserInfoByToken`，JSON `{}`，携带该请求头。成功要求HTTP200、有效JSON、`appcode === '0'`及非空 `map.userId`；返回还有 `userName`、功能权限等。仅解析令牌或看到Cookie不足以判定登录有效。

原站JavaScript对业务 `appcode == '401'` 清理会话并转到 `/TRANS/login`；尚无真实失效响应样本。网络超时或5xx应保持未验证，不能当已登录，也不能清掉仍可能有效的会话。后续需捕获业务请求令牌、加密保存，并恢复相关sessionStorage；同时识别CAS登录页与业务登录页。校验有效后恢复业务首页。

## 查询链路

所有以下业务接口均为同源POST JSON，请求头使用 `Access-Token`。正常响应为 `{ msg, appcode: '0', map }`；`map`可能为对象或数组。

| 用途 | 路径 | 关键请求字段 | 结果 |
| --- | --- | --- | --- |
| 全部经办列表 | `/TRANSB/busiInstanceInfo/queryAllDealtBusiList` | 日期、事项、机构等筛选 | `map[]`办件 |
| 办理过程 | `/TRANSB/busiInstanceInfo/queryBusiInstanceLog` | 有流程时`ywlsh`，无流程时`lsh` | `map[]`历史环节 |
| 流程主体信息 | `/TRANSB/busiInstanceInfo/queryBusiInstanceHandler` | `ywlsh` | 主体/经办资料 |
| 流程表单 | `/TRANSB/procFormdata/queryProcFormData` | `piid=ywlsh`、`usecache='1'` | `map.data`中的表单JSON |
| 申报主体信息 | `/TRANSB/grpspBusiness/queryGrpspHandler` | `lsh`、`ckbz='1'` | 主体/经办资料 |
| 申报详细信息 | `/TRANSB/busiSbxx/querySbxxTempInfo` | `lsh`、`ckbz='1'` | 主体、表单、申请/受理资料 |

原页面明确按 `row.ywlsh` 是否存在切换详情组件：有值传 `piid=row.ywlsh`；无值传 `lsh=row.lsh`。请求与列表编号在内存逐条匹配，确认上述关联成立，没有把两种编号互换。

办理记录目标的最小链路是“登录校验 → 全部经办列表 → 逐案办理过程”。列表已提供主体名称、事项、状态和部分人员/日期，缺项再按两条分支补主体或表单。流程图、页面编译、附件下载、机构字典等不是逐案采集办理过程的必要请求。材料清单接口已捕获，但不意味着必须下载材料文件。

## 列表与实际样本

“全部经办”按接收时间查询：11月20日至27日返回29条，11月1日至30日返回152条。后者增加业务经办单位筛选后仍为同一152条，不能据此推断具有全市全部单位权限。

152条涉及4种原站事项：小微企业社保补贴申领143条、吸纳脱贫人口社保补贴和岗位补贴2条、员工制家政服务企业备案1条、员工制家政服务企业社保补贴6条。个人已办历史另出现一次性就业补贴等事项，但没有覆盖助手全部十项的详情；不能宣称十项已经逐项验收。

列表有130条带 `ywlsh`，22条只有 `lsh`，没有两种编号都为空的样本。22条无流程号办件中，4条“申请完成”、18条“受理不通过”。实际选中的无流程号样本，使用 `queryBusiInstanceLog({lsh})` 成功返回申请、受理两条记录，因此不能套用“无流程号就跳过办理记录”的规则，更不能删掉未进入流程的办件。

列表字段依据原前端列定义：

| 字段 | 原页面含义 |
| --- | --- |
| `lsh` / `ywlsh` / `slsh` | 申办流水号 / 业务流水号 / 市受理流水号 |
| `sxid`、`sxmc`、`qxid`、`qxmc` | 事项及情形标识、名称 |
| `ywztmc`、`ywztbh`、`ywztlx` | 申请人或单位名称、号码、主体类型 |
| `sqsj`、`kqsj`、`slsj`、`bjsj` | 申请提交、接收、受理、办结时间 |
| `ywslr`、`dqfpr`、`ywjbdw` | 业务受理人、当前分配人、业务经办单位 |
| `ywzt`、`dqhj`、`dqhjmc`、`ywzy` | 业务状态、当前环节及名称、业务摘要 |

样本中申请提交时间、受理人、办结时间存在缺值，不能把空值补成接收时间或当前登录人。列表不是工作人员的完整办理历史，历史人员必须从过程接口获取。

## 办理过程字段

| 字段 | 原页面含义与处理 |
| --- | --- |
| `hjbt`、`hjlx`、`hjmc` | 环节名称、环节类型、自定义环节名称 |
| `cjsj` | 环节接收时间 |
| `czr`、`czsj` | 操作人、操作时间 |
| `spr`、`sprq` | 审批人、审批时间 |
| `spyjmc`、`spsm` | 审批/公示结果、意见说明 |
| `wcsj` | 完成时间；撤回和补正环节有各自展示含义 |
| `gssj`、`zhbz` | 公示开始时间、撤回标志 |
| `yqjgmc` | 办理机构名称，样本可为空 |

上述过程时间在实际样本为14位 `YYYYMMDDHHmmss`，列表时间主要为 `YYYY-MM-DD HH:mm:ss`，需分别解析为北京时间。操作人与审批人、接收/操作/审批/完成四个时刻要分别保留，不能为套用广东人社的七列模型而丢弃。

原页面将“异议不成立/没有异议/无异议”展示为“公示通过”，“异议成立”展示为“公示不通过”。后续可以同样提供展示结果，但要保留原始业务结果。申请行为、窗口操作、未完成环节和撤回记录均保留；窗口经办量统计另按环节及实际人员判断，不能把申请人的提交算作工作人员经办。

两条实际分支样本的办理记录均缺少 `logid`，不能以空 `logid` 去重，也不能只按人员或时间合并。建议按办件保存完整过程快照，每次成功重采替换该案快照，保留同一快照内合法的重复操作；真实事件编号存在时再作额外关联。

## 日期与分页

| 原站日期条件 | 请求字段 | 依据 |
| --- | --- | --- |
| 接收时间 | `jssj`范围、`jsqssj`、`jszzsj` | 三次真实全部经办查询 |
| 受理时间 | `slsj`范围、`slqssj`、`slzzsj` | 原前端提交逻辑，未单独实测 |
| 办结时间 | `bjsj`范围、`bjqssj`、`bjzzsj` | 原前端提交逻辑，未单独实测 |

抓包的全部经办起止参数保留了14位时分秒，例如月初、月末的15点多；实现时须明确自然日起止边界，避免照抄时分秒导致首日上午或末日晚间漏数。接口边界的闭合规则仍需小样本在线核对。个人已办使用的8位日期规则不能直接套到该接口。

建议先提供原站确实支持的日期类型，默认本月接收时间。用户选定的日期只用于定位办件，之后获取这些办件的全部办理过程，不再次裁剪历史环节。若改用申请日期，不能把 `jsqssj/jszzsj` 改个界面标签冒充申请日期：原站这里没有相应提交条件，且本次部分 `sqsj` 缺失，需另行核对数据来源。

本次接口一次返回完整数组，前端 `BasicTable`以该数组作本地分页，总数显示数组长度。未观察到服务端页码、总数接口或游标，不应自行添加翻页参数。大范围返回上限尚未验收；后续可按日期拆小范围，再合并办件编号。

## 与现有助手的衔接建议

1. 保持当前系统ID及授权目录，替换它的目录占位插件，不重复注册或重新签发现有权限。
2. 沿用该系统已配置的单线程任务执行，列表与逐案过程按顺序请求；同一批可复用列表快照，减少多事项重复请求。
3. 办件保存两套编号及可核验关联。后续申报进入流程时，只有关联充分才合并已有记录；不凭相同企业名或名称相似合并。
4. 复用“列表＋办理记录”展示模式，同时扩展当前只识别广东人社四项的展示/导出判断，保留深圳特有的操作与审批字段。建议Excel分“办件列表”“办理记录”两张表，通过办件编号关联。
5. 单案过程失败时保留办件列表并标记未补齐，允许重试；不能把失败写成“0条办理记录”。网络超时重试与会话失效分开处理，不执行任何签领、退回、审批、领取等写操作。
6. 原站“吸纳脱贫人口社保补贴和岗位补贴”是合并事项，助手目前分两项。具体拆分缺少业务标志依据，应先按源事项关联并避免重复计数，不能只按界面名称硬拆。其余未捕获事项的详情字段仍需后续少量验证。

## 已见异常与验证边界

原站自身曾返回HTTP200但 `appcode='1'` 的 `queryBusiHjPageInfo`，以及HTTP504的 `queryBusiSituShysInfo`。因此成功判断必须同时核对业务码，局部页面接口失败也不等同于退出登录。核心全部经办和两种办理过程查询样本均成功。

本轮只分析用户已提供的HAR、相关静态页面代码和现有广东人社实现，不复用抓包凭据访问现场，不修改回流逻辑或线上授权。原始账号、Cookie、令牌、真实办件号、人员与企业资料均不写入本文。脱敏接口清单与统计依据留在本地 `private/deploy/shenzhen-integrated-analysis-20261127/`。
